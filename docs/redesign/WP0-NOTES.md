4 Oct 2026. Where WP0 departs from SPEC revision 2, and why. Every item is the smallest change that makes the SPEC's own code work against the installed packages (Next 14.2.35, React 18.3.1, motion 12.43.0, lenis 1.3.26, typescript-eslint 8.70, @types/react 18.3.31) or pass its own checks. Nothing here changes a contract in §4.3.

## Things builders should know

- **Timeline start state** (`lib/timeline.ts`). A timeline first rendered on the server starts at `endMs` with `done = true`, because the server snapshot is "reduced". That keeps the server HTML in its final state. The section decides when to play from the start: call `restart()` at mount when the element is below the viewport (rule 2.4.7). A timeline first mounted on the client, with motion allowed, starts at 0. With `loopGapMs` it restarts by itself after the gap.
- **Hero stub.** `hero.module.css` already holds §5.1.1's layout verbatim, so the stub puts the real Field on the real Horizon: the apex is at 569.7 at 1440x900 and 438.9 at 390x844, Δ 0. WP1 owns the file. `Chips` takes `className`, so the module's `.chips` class reaches it.
- **WP-internal stubs** have placeholder props marked "WP owns these props": `ChainList`, `ChainRow`, `Stopwatch`, `Artefact`, `ActRail`, `useRun`, `RunStep`, `Divider`, `Guarantee`, `Roas`, `Paid`, `Share`, `Orbit`, `Readout`, `Locks`, `GiantWordmark`, `Launcher`, `PromoCard`, `sky/gl.ts`, `sky/shader.ts`, `sky/watchdog.ts`. Every §4.3 export is typed exactly as the contract.
- **Lab pages** are client pages that call `notFound()` in production. They render inside `LabFrame`, whose children are `(audience) => ReactNode`, and the audience comes from `?a=`. A lab page for a section passes the deferred audience.
- **CSS modules** trigger a harmless Tailwind warning in the dev log ("The `content` option … is missing"). PostCSS runs Tailwind on every `.module.css`, which has no `@config`. The modules contain no Tailwind directives, so nothing is generated (§2 rule: never `@apply` or `theme()` in a module).
- **`measure` builds into `.next-measure`.** On its first run Next rewrote `tsconfig.json`: it pretty-printed the file and added `.next-measure/types/**/*.ts` to `include`. Commit that once (§7.3).

## Budget ruling needed (before WP1 to WP8 start)

`npm run measure` passes today, with the motion + lenis line at 44 kB (D13, provisional). Two lines of §7.1 need the lead: the libs figure, and the first-load figure, which no longer adds up once the libs figure is real.

First load as §7.3 defines it (the union of `rootMainFiles`, `/(site)/layout` and `/(site)/<route>/page`), every WP1 to WP8 body still a stub, attributed by module:

| Part | Size |
|---|---|
| **First load** | **153.8 kB** of 160 kB. **6.2 kB headroom** (measure prints it) |
| Framework (rootMainFiles, plus next's process polyfill and next/font stubs outside them) | 86.3 kB |
| motion + lenis | 42.1 kB: motion-dom 23.7, framer-motion 10.9, lenis + lenis/react 5.6, motion-utils 1.9 |
| Site (site code, copy, tokens, Phosphor icons) | 25.3 kB of 45 |

Next's own route table prints 144 kB, because it leaves out the layout's chunks.

**The arithmetic.** §7.1's lines were built to fit: 87 + 26 + 45 = 158 ≤ 160. With the real library figure they do not: 86.3 + 44 + 45 = 175.3 kB. At 160, the site line can never use its 45 kB: framework and libraries take 128.4, so all site code shares 31.6 kB, and the stubs already use 25.3. That leaves 6.2 kB for the hero's Headline, Chips, Toasts and Sky loader, plus every below-the-fold section, whose code today lands in first load because `Landing.tsx` imports them statically. **160 fails as soon as builders land code.**

**Options for the first-load line:**

- **A. Raise it to 176 kB** (86.3 + 44 + 45, rounded up), and keep 160 as the stretch goal. No structural change, and every other line keeps its meaning.
- **B. Keep 160, and take the below-the-fold sections out of first load now:** `next/dynamic` (with SSR) in `Landing.tsx` for WorkSection, RunStage, NumberSection, AgentsBand, Connects, Close, Footer and Promo. They already sit in `<Suspense>`. Use `next/dynamic`, not `React.lazy`: Next 14's app-router `next/dynamic` emits the lazy chunk's stylesheet links in the server HTML (`PreloadCss` in `next/dist/shared/lib/lazy-dynamic/loadable.js`), and `React.lazy` would ship the CSS modules with no link in the static HTML, so the sections would paint unstyled until hydration. Costs: those sections hydrate when their chunk arrives (the server HTML shows meanwhile), and `measure`'s chunk-deny scan, which covers only first-load chunks and the sky chunk, must also scan the lazy section chunks (about 5 lines, the same addition §7.3 assigns WP-F for lever 1). The hero alone still has to fit the 6.2 kB, so the Toasts (desktop only, gate G10) may need the same treatment.
- **C. Lever 1** (one chunk per audience) is a narrower version of B: it removes only the other audience's sections.
- **Lever 2** (async LazyMotion features) saves 3.1 kB of library code (measured: first load 150.5, motion + lenis 38.8). It moves only `features-animation` (gestures, exit, animation state); the visual element and the animation engine stay, because the imperative `animate` and the `m` components need them. The pill then needs a CSS resting position. Keep it in reserve.

**Suggested ruling:** amend §7.1 to "motion + lenis ≤ 44 kB, attributed by module" (D13, already in `measure`), and either take A, or take B before WP1 to WP8 start so that builders measure against the structure that ships. Applying A is one line: `BUDGET.firstLoad` in `scripts/measure.cjs`. B is a `Landing.tsx` change plus the deny-scan addition, and WP0 can make both on the lead's word.
